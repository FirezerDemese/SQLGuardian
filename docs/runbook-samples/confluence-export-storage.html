Storage and Volume Procedures

Owner: Platform Data Engineering. Escalation: #db-oncall, then Infrastructure for anything at the SAN or hypervisor layer. Last reviewed: 2026-07-21.

Data or log volume above 80 percent

Applies to all SQL Server volumes. E: is the data volume, L: is the log volume and X: is the local backup staging area on every instance in the estate.

  1. Identify what is actually consuming the volume before requesting more space. Infrastructure will ask and we should already know.
  2. If the volume is X:, check backup retention first. Staged backups older than 7 days are already copied to the vault and are the intended thing to remove.
  3. Confirm the vault copy exists for anything you plan to delete. Check the vault catalogue, not the local file dates.
  4. If the volume is L: and a single log file is the consumer, follow the transaction log procedure instead. Do not delete anything on L:.
  5. Raise a storage extension request with Infrastructure using the standard template. Include the growth rate over the last 30 days.
  6. Do not run DBCC SHRINKFILE against a data file to reclaim space during business hours. Shrink is single-threaded, fully logged, and leaves fragmentation we then have to rebuild.

Rollback: a storage extension is not reversible without Infrastructure. File deletion is not reversible at all - this is why the vault check is step 3 and not step 5.

SQL Agent job failed overnight

The overnight schedule is: backups 22:00, warehouse load 23:30, index and statistics maintenance 02:00 Sundays only.

  1. Read the failing step output, not the job-level summary. The job history summary almost never contains the actual error.
  2. If the failed job is a backup job, treat it as a Tier 1 incident and follow the backup procedure. Do not simply re-run it.
  3. If the warehouse load failed, check whether it failed on a lock timeout. If so it is a contention incident, and re-running it into the same contention will fail the same way.
  4. Re-run the job only once the cause is understood, and only with the duty manager informed if it is outside its normal window.
  5. If the job has now failed on three consecutive nights, raise a problem record. We do not keep re-running a job that is telling us something.

Rollback: whatever the job did is done. sp_stop_job halts a run in progress but does not undo completed steps.
